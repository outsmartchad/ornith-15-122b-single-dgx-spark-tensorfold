# How Ornith 1.5 122B reads a prompt and generates text

## How the model works

Imagine sending “The passcode is violet” in one paragraph and asking for the passcode several pages later. The model receives a sequence of integers. A chat template marks who said what, and a **tokenizer** converts the text and its markers into token IDs. A token can represent a word, part of a word or punctuation. For each ID, the model looks up a row in a learned table. This **embedding** supplies the token’s initial vector of 3,072 numbers. “Violet” can occupy one or more positions depending on tokenization. Everything below applies to individual positions. [Original Ornith configuration](https://huggingface.co/ornith-ai/Ornith-1.5-122B/blob/38c106ad/config.json) · [Ornith model card](https://huggingface.co/ornith-ai/Ornith-1.5-122B)

A learned **weight** is available to every conversation. An embedding table, for instance, keeps the same row for the same ID. The vector calculated *after* the model reads “violet” in context belongs to that particular sequence. It can now carry information about a passcode as well as a color. Some of the numbers calculated for the sequence live only while a layer runs, while others are saved so the next token can use earlier information. Ornith has two quite different ways to keep this **request state**. Their difference explains much of its memory use at long context lengths. [Architecture configuration](https://huggingface.co/ornith-ai/Ornith-1.5-122B/blob/38c106ad/config.json) · [Qwen3.5-MoE reference implementation](https://github.com/huggingface/transformers/blob/v5.8.1/src/transformers/models/qwen3_5_moe/modeling_qwen3_5_moe.py)

### How the passcode travels through 48 layers

Ornith uses the Qwen3.5-MoE decoder. In each group of four layers, the first three mix information using Gated DeltaNet (GDN). The fourth uses full causal attention. The group repeats twelve times, for 36 GDN layers and 12 full-attention layers. Each of the 48 also transforms its result through a mixture of experts. The input to each major computation undergoes RMS normalization, which rescales a vector according to its typical magnitude. A residual connection adds the update back to the incoming vector. Earlier information can therefore continue forward while a layer contributes something new. [Layer schedule](https://huggingface.co/ornith-ai/Ornith-1.5-122B/blob/38c106ad/config.json) · [Decoder, normalization and MoE implementation](https://github.com/huggingface/transformers/blob/v5.8.1/src/transformers/models/qwen3_5_moe/modeling_qwen3_5_moe.py)

**A GDN layer updates an association.** It projects the input into several views, including a key, a value and a query. A short convolution spanning four positions mixes nearby features. Imagine that the state already maps a feature resembling “passcode” to a rough value. The layer computes how much of the old state to retain, reads its existing prediction for the incoming key and uses the difference from the new value to correct the association. A learned gate controls the strength of that correction. The query reads the updated state to supply an output for this position. The passcode is a teaching example. A real state holds many overlapping numerical associations with learned features. [Gated Delta Networks paper](https://arxiv.org/abs/2412.06464) · [Reference implementation](https://github.com/huggingface/transformers/blob/v5.8.1/src/transformers/models/qwen3_5_moe/modeling_qwen3_5_moe.py)

The state of a GDN head has a fixed size as the sequence grows. The config lists 16 key heads and 64 value heads with 128 dimensions for each key and value head. TensorFold budgets for a recurrent matrix for each of 64 heads per GDN layer, plus short convolution tails. The next paragraph of our prompt changes those matrices in place. Repeated updates can preserve, modify or weaken an earlier association. This design gives the decoder a way to process very long inputs with bounded recurrent state per sequence. [Model dimensions](https://huggingface.co/ornith-ai/Ornith-1.5-122B/blob/38c106ad/config.json) · [TensorFold state accounting](https://github.com/MiaAI-Lab/Ornith-1.5-122B-TensorFold/tree/0c8fd6a0d1e2ece7557978a7d8c3d96d137eb075)

**A full-attention layer can look directly at earlier positions.** On layer four, for example, a position in the question computes a query expressing what to look for. Earlier positions provide keys describing what they match and values describing what information to return. Query/key scores determine how strongly each value contributes. Only current and past positions are eligible. Ornith has 32 query heads and just 2 key/value heads, so 16 query heads share each KV group. Its rotary position settings apply to a quarter of the head dimension, giving part of the query/key representation information about position. The attention output also has a learned gate. [Full-attention configuration](https://huggingface.co/ornith-ai/Ornith-1.5-122B/blob/38c106ad/config.json) · [Attention implementation](https://github.com/huggingface/transformers/blob/v5.8.1/src/transformers/models/qwen3_5_moe/modeling_qwen3_5_moe.py)

The server can store the keys and values at each full-attention layer after they are computed. When the question reaches the end of the prompt, its query can match a key near the original passcode without recalculating the entire prefix. That retained history grows as more tokens arrive. GDN layers offer progressively updated summaries, and regularly spaced full-attention layers offer access to individual earlier positions. An exact-retrieval test exercises this combined system. It does not reveal which head or state component carried the answer. [Model architecture](https://huggingface.co/ornith-ai/Ornith-1.5-122B/blob/38c106ad/config.json) · [Published retrieval samples](../results/benchmark-2026-11-21.json)

**An expert layer transforms the current position.** Its router scores 256 learned feed-forward networks and selects eight. Each selected expert takes the current vector, computes a gated nonlinear transformation with an intermediate width of 1,024, and projects it back. The layer mixes their results with the routing weights. A separate 1,024-wide shared expert runs at every position. Its own gate controls its contribution before the two paths are summed. These operations act on information already gathered by the token mixer. A token representing punctuation can use different weights from a token representing a passcode character. Every expert still has to be available when chosen. [Router and shared expert implementation](https://github.com/huggingface/transformers/blob/v5.8.1/src/transformers/models/qwen3_5_moe/modeling_qwen3_5_moe.py) · [Checkpoint dimensions](https://huggingface.co/ornith-ai/Ornith-1.5-122B/blob/38c106ad/config.json)

After layer 48, final normalization and a separate output projection turn the last prompt vector into scores for 248,320 possible token IDs. Such a score is called a **logit**. A sampler uses the scores to choose the first piece of the reply. Under greedy decoding it chooses the highest score. With sampling, the model assigns probabilities to eligible pieces. After it chooses the first piece of “violet”, the server extends the sequence, updates its saved state and predicts the next piece until a stop condition. A detokenizer turns the accepted IDs back into text. A chat parser can separate reasoning content from the answer. [Output head and vocabulary](https://huggingface.co/ornith-ai/Ornith-1.5-122B/blob/38c106ad/config.json) · [Chat format](https://huggingface.co/ornith-ai/Ornith-1.5-122B)

Text prompts skip the image encoder. For an image, Ornith’s vision transformer processes patches of 16 pixels per side. It has 27 layers, 16 attention heads and an internal width of 1,152. A merger combines neighboring features in 2-by-2 spatial groups and projects them to the decoder’s 3,072 dimensions. The image features enter the sequence where the template placed image positions. The language decoder can then generate text grounded in the image. This TensorFold build enables images and rejects video. Its published local timing and retrieval measurements use text. [Vision configuration](https://huggingface.co/ornith-ai/Ornith-1.5-122B/blob/38c106ad/config.json) · [Upstream image support](https://github.com/MiaAI-Lab/Ornith-1.5-122B-TensorFold/tree/0c8fd6a0d1e2ece7557978a7d8c3d96d137eb075)

## How this recipe runs it on one DGX Spark

### Which weights fit on the machine

The target is Mia AI Lab’s EXL3 EAQ v1 conversion of Ornith. “4 bpw” refers to an average number of bits per weight. The quantizer reports **4.049 bits per weight for the trellis-coded tensors** and **4.19 overall across 125.09 billion parameters** when the high-precision components are included. “122B” is the model’s published name. The nine weight shards total 65.54 billion bytes, about 61.0 GiB. The accompanying IncoAI draft adds about 1.86 GB on disk. This explains the recipe’s advice to allow around 63 GiB for model files, plus room for the image and working caches. [EXL3 conversion report](https://huggingface.co/Mia-AiLab/Ornith-1.5-122B-EXL3-EAQv1-4-bpw/blob/9c5c913b3de1eef901520d6fedaf450044ea0423/README.md) · [Deployment inventory](https://github.com/MiaAI-Lab/Ornith-1.5-122B-TensorFold/tree/0c8fd6a0d1e2ece7557978a7d8c3d96d137eb075)

A single routed expert makes the packing concrete. The storage map for the first layer’s expert 0 down-projection records 1,572,864 bytes in a 16-bit integer `.trellis` tensor, two half-precision vectors called `.suh` and `.svh`, and a four-byte `.mul1` value. The packed integers hold codes for many weights. Their container type is distinct from the effective bits per learned weight. The same map records the embedding table as one ordinary BF16 tensor. This is why multiplying every parameter by four bits misses both side data and the decisions to preserve precision for particular components. [Per-tensor storage map](https://huggingface.co/Mia-AiLab/Ornith-1.5-122B-EXL3-EAQv1-4-bpw/blob/9c5c913b3de1eef901520d6fedaf450044ea0423/quantization_config.json) · [Shard index](https://huggingface.co/Mia-AiLab/Ornith-1.5-122B-EXL3-EAQv1-4-bpw/blob/9c5c913b3de1eef901520d6fedaf450044ea0423/model.safetensors.index.json)

| Component | Released representation |
| --- | --- |
| Routed expert projections | 4 bits, about 58.28 GB in total |
| Shared experts, quantized GDN projections and full-attention projections | 5 bits |
| Language-model output head | 6 bits |
| Auxiliary multi-token prediction (MTP) layer | 4-bit projections, 16-bit norms |
| Vision tower, token embeddings, router gates and norms | 16 bits |

The converter compared next-token predictions with BF16 over 92,067 reference assistant tokens and found 96.7% top-choice agreement. Its evaluation used 100 held-out conversations, a different chat template and contexts up to 4,096 tokens. The result measures the effect of the weight conversion on those inputs. The Spark retrieval benchmark tests a different question, whether this deployment returned one specific embedded key after a much longer input. [Quantization measurements and evaluation method](https://huggingface.co/Mia-AiLab/Ornith-1.5-122B-EXL3-EAQv1-4-bpw/blob/9c5c913b3de1eef901520d6fedaf450044ea0423/README.md) · [Local benchmark client](../benchmark.py)

### From an HTTP request to verified output

`./serve.sh download` checks out deployment commit `0c8fd6a0`, pulls the ARM64 image and verifies its digest. It fetches target revision `9c5c913b` and DFlash2 draft revision `a5ed7396`. `start` invokes the pinned upstream launcher offline. The container mounts the model cache read-only and has a separate kernel cache. A client sends an OpenAI-style chat request to `127.0.0.1:18893`. TensorFold’s native Zig server renders the template, admits the sequence, and schedules GPU work alongside other active sequences. The wrapper selects five slots and the model endpoint reports 262,144 positions per request. [Recipe wrapper](../serve.sh) · [Pinned upstream launcher](https://github.com/MiaAI-Lab/Ornith-1.5-122B-TensorFold/blob/0c8fd6a0d1e2ece7557978a7d8c3d96d137eb075/start.sh) · [Endpoint report](../results/benchmark-2026-11-21.json)

During **prefill**, all prompt IDs are known. TensorFold can process chunks of prompt rows together, use its chunked GDN scan, and group rows that need the same expert. The patched implementation includes tensor-core attention, fused mixed-width expert kernels and support for 8,192-row prompt passes. During **decode**, each request supplies new rows as tokens become available. The runtime can group work across users, overlap the shared expert on another GPU execution stream, and use narrow target verification windows. These implementation details explain which operations can share work. The benchmark has no GPU trace to assign a percentage of the measured speed to each optimization or to CUDA graph replay. [Pinned implementation and patches](https://github.com/MiaAI-Lab/Ornith-1.5-122B-TensorFold/tree/0c8fd6a0d1e2ece7557978a7d8c3d96d137eb075)

For decode, the recipe uses an external **DFlash2** model even though the packed target also contains a one-layer MTP predictor. The draft reads features from target layer IDs 1, 7, 14, 20, 26, 32, 39 and 45. Its six sliding-attention layers operate on a masked block, with a configured 2,048-position attention window. Given an anchor token, it predicts the remaining positions of a 16-position block together. Two-tap dynamic convolutions pass local information between neighboring draft positions. A rank-256 selector considers the top 16 candidates per position and scores adjacent choices to form one consistent continuation. The draft’s 15 possible continuations per round are independent of the target router’s eight experts per layer. [Draft configuration](https://huggingface.co/incoai/Ornith-1.5-122B-DFlash2/blob/a5ed7396f5f9e5b1abf7ff50b7899a3186961432/config.json) · [DFlash2 model card](https://huggingface.co/incoai/Ornith-1.5-122B-DFlash2/blob/a5ed7396f5f9e5b1abf7ff50b7899a3186961432/README.md) · [Runtime patch for 16-position blocks](https://github.com/MiaAI-Lab/Ornith-1.5-122B-TensorFold/blob/0c8fd6a0d1e2ece7557978a7d8c3d96d137eb075/patches/0007-qwen35-exl3-dflash2-drafter.patch)

Suppose candidate lists suggest pieces for both “violet” and “violent”. The selector can favor a second piece that makes sense after the chosen first piece. Only target verification can authorize those pieces for the reply. At the first disagreement the rest of that proposed suffix is discarded, and the next round starts from the accepted prefix. Several accepted pieces can share one expensive target evaluation. Rejected rows still cost GPU work and can activate extra experts. Upstream documents a separate experimental MTP path and greedy comparisons with drafting off. The local sampled prose report records output throughput and latency, leaving its per-round draft acceptance unmeasured. [DFlash2 algorithm](https://inco.ai/blog/dflash2/) · [Upstream comparisons](https://github.com/MiaAI-Lab/Ornith-1.5-122B-TensorFold/tree/0c8fd6a0d1e2ece7557978a7d8c3d96d137eb075) · [Local results](../results/benchmark-2026-11-21.json)

### Interpreting capacity and latency

TensorFold stores full-attention KV in FP8 in this recipe. The upstream estimate for one full window is 3.05 GiB of KV including scales, calculated from 12 attention layers, 2 KV heads, head width 256 and 262,144 positions. Each sequence also needs about 160 MiB of GDN state and convolution history. The allocator leaves a 10 GiB system reserve and admits work against the remaining unified memory. Five full windows represent 1,310,720 positions across all requests. Five short requests and a separate single 200K request were measured. The sampled GPU-process peak across the run was 90.4 GiB. Docker imposed no fixed memory cap. [Upstream memory calculation](https://github.com/MiaAI-Lab/Ornith-1.5-122B-TensorFold/tree/0c8fd6a0d1e2ece7557978a7d8c3d96d137eb075) · [Local memory samples and context limit](../results/benchmark-2026-11-21.json)

With a 400-token budget, thinking enabled and temperature 0.7, one stream reached **61.3 output tokens/s**. Five streams delivered **100.2 tokens/s combined** and a median **20.4 per request**. These are the fastest aggregate waves from three repetitions at each concurrency. Median time to first reasoning or answer token rose from 158 ms to 512 ms. Separate fresh prompts measured **16.64 s to first token at 32,740 tokens** and **202.70 s at 199,952**, equivalent to 1,968 and 986 uncached input tokens/s. Both returned the exact synthetic key. To estimate the wait before a long document query starts answering, use the prefill measurements. To estimate how quickly an answer streams once it starts, use per-request decode.
